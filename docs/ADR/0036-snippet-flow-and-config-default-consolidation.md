# ADR 0036: Fix the Snippet-Flow Defect Class + Consolidate Divergent Config Defaults

Date: 2026-06-12

## Status

Accepted. Repairs the content-extraction path introduced in Sprint 7
([type-aware extractor](../SPEC.md)) and hardened in Sprints 13/17/19. Does not
change any contract/DTO (no version bump). Complements [ADR 0025](0025-dual-source-text-representation.md)
(dual-source `{stem}`/`{title}`/`{snippet}` template).

## Context

A run over a folder of 57 PDFs produced 2 top-level groups where richer
separation was expected. Investigation traced this to **document content never
reaching the embedder** — and showed it was not one bug but a *class* of bugs
generated by one structural weakness: **the same configuration knob has
divergent default values scattered across three layers**
(`config.py::get_system_defaults()`, `config/default.toml`, and the inline
`.get(key, DEFAULT)` fallbacks in `core/registries.py`).

The content snippet was lost or corrupted at three independent points:

- **F1 — extractor dispatch never matched (root cause).** The scanner stores the
  extension **without** a leading dot (`fs_scanner.py`: `p.suffix.lower().lstrip(".")`
  → `"pdf"`), but `type_aware.extract` compared it against **dotted** keys
  (`{".pdf", ".txt", …}`). Every branch fell through, so **every file** — PDF,
  DOCX, PPTX, image, *and* plain text — received an **empty snippet**. Present
  since the extractor's first commit (Sprint 7, `5b8c1eb`); embeddings and folder
  names therefore ran on filename stem + extension only, the entire time.

- **F2 — `snippet_size` not wired.** `pipeline.run_pipeline` called
  `extractor(fr, {})` with an empty dict, so the extractor fell back to its own
  hard-coded default and ignored the configured `scanner.snippet_size` (4096).
  The extractor's own default was additionally a *divergent* `1024`, contradicting
  the `4096` in both the system defaults and `config/default.toml` — and the 4 KB
  intent already documented in SPEC (Sprints 13/17/19).

- **F3 — cache text fetch ignored `content_hash`.** The embedding cache PK is
  `(key, model_id, content_hash)`, but `get_many_texts` (used by naming) filtered
  only `(key, model_id)`. The moment a file's preprocessed text changes — i.e.
  exactly when F1/F2 are fixed — a prior run's stale row (e.g. the old
  empty-snippet text) could be served to the namer nondeterministically,
  violating the determinism rule. Clustering was unaffected (it uses freshly
  computed vectors); naming was not.

- **F8 (latent) — snippet-less template fallback.** The `type_aware` extractor's
  output is only embedded if the preprocess template emits `{snippet}`. Pairing
  `type_aware` with a snippet-less template (as the system-default template and
  the registry fallback both are) silently discards extracted content with no
  error.

The tests could not catch F1/F2 by construction: every type-aware extractor test
hand-built `FileRef(ext=".pdf")` **with a dot** — a value the real scanner never
emits — and always passed `snippet_size` explicitly, bypassing the pipeline's
wiring. The one real-pipeline test asserts structure only, and the pipeline
clears `extracted`/`preprocessed` before returning, so snippet content was
unobservable there.

## Decision

1. **F1 — normalize the extension at dispatch.** `type_aware.extract` computes
   `ext = "." + file.ext.lower().lstrip(".")`, so both bare (`"pdf"`, production)
   and dotted (`".pdf"`, legacy fixtures) inputs dispatch correctly.

2. **F2 — wire `snippet_size`.** The pipeline passes
   `{"snippet_size": int(sc.get("snippet_size", 4096))}` to the extractor, and the
   extractor's own fallback is raised `1024 → 4096` to mirror the single source of
   truth in `config.py::get_system_defaults()`.

3. **F3 — pin cache reads to the embedded `content_hash`.** `get_many_texts`
   accepts an optional `content_hash_by_key` map and returns the row matching the
   requested hash; the pipeline builds that map from the current run's
   `EmbeddingRecord.content_hash`. No embedding-provider version bump is needed:
   the embedder implementation is unchanged — only the *input text* changes, and
   `content_hash` already invalidates stale **vectors**; this change extends the
   same discipline to stale **text**.

4. **Config-coherence guard (prevents the F8 class).** `validate_config` now
   rejects `scanner.extractor = "type_aware"` paired with a `preprocess.template`
   that omits `{snippet}`, failing loudly instead of silently dropping content.

5. **Collapse divergent defaults.** The hdbscan registry fallback for
   `min_cluster_size` is aligned `5 → 4` to match the system default and the
   agglomerative fallback (this path is always injected by the proposer/config in
   practice; the change removes drift risk, not behavior).

6. **Restore test fidelity.** All hand-built extractor fixtures use the bare ext
   the scanner emits (`ext="pdf"`); a shared `make_file_ref` factory in
   `conftest.py` enforces this for future tests; and a new
   `test_snippet_flow_regression.py` guards F1 (via the **real** scanner), F2, F3,
   and the coherence guard.

## Consequences

- Document content now flows end-to-end: extractor → `{snippet}` template →
  embedder → cache → namer. Embeddings and names reflect content, not just
  filenames.
- **The "7 groups" figure is not a target.** Because content was empty since
  Sprint 7, any prior baseline was filename-only; the true content-based grouping
  is *re-measured*, not "restored." Establishing it belongs to the empirical
  characterization (Ch. 4).
- **Stale caches must be cleared before validating.** Existing rows hold
  old empty-snippet text under stale `content_hash`es; F3 prevents them
  contaminating naming, but a clean cache is the honest way to re-measure.
- `config/sbert_ollama_llama3_1.toml` remains a *content-blind* preset (basic
  extractor + snippet-less template + kmeans). It is internally consistent, but
  it does **not** exercise the content path; the CLI default (`config/default.toml`,
  type-aware + hdbscan) is the stack to validate against. Flagged for a future
  alignment pass.
